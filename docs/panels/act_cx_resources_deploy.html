Auth

CX exige identificación antes de cualquier llamada. Usamos gcloud en lugar de una clave de servicio fija porque es más seguro — el token expira, no hay credenciales que robar.

gcloud auth print-access-token — se obtiene una vez al inicio y se reutiliza en todas las llamadas. Si expira, el Paso 1 falla con 401.
Cabeceras obligatorias

Google necesita saber quién eres, en qué formato hablas y a qué proyecto cargar el uso. Sin estas tres cabeceras la API rechaza la llamada aunque el token sea válido.

Authorization: Bearer <token>
Content-Type: application/json
x-goog-user-project: <GCP_PROJECT>
Agente de referencia

El agente es Petal 1.0 en Google Cloud. Todos los scripts leen su ID y región desde un único archivo — así si cambia, solo se toca en un sitio.

Petal 1.0 — región europe-west1. ID y proyecto en definitions/agent.yaml.

Paso 1 — Inventario CX
1.1 — Pre-flight check (automático)

Antes de lanzar las 12 llamadas LIST, el script verifica que la autenticación y la conectividad con CX funcionan. Si falla aquí, el error es inmediato y claro — no a mitad del inventario.

Antes de llamar a cualquier función inventory_*(), ejecutar:
1. get_headers() — verifica que gcloud está autenticado y genera token fresco.
   Si falla → RuntimeError claro: "gcloud no autenticado. Ejecuta gcloud auth login."
2. GET {PARENT} — un GET al endpoint del agente para verificar conectividad y permisos.
   Si falla → error claro con status code y mensaje de la API.
Sin este check, un fallo de auth produce errores HTTP 401 a mitad de las 12 llamadas,
sin saber en qué recurso falló. Con el pre-flight, el fallo es inmediato y explícito.
Qué hace

Antes de desplegar nada, necesitamos saber qué hay ahora mismo en el draft del agente Petal. El draft es el estado editable de CX — no la versión que está corriendo en staging para test cases. Este paso hace una foto de ese borrador: cuántos playbooks, examples, tools y demás recursos existen en CX en este momento.

Llama a las 12 funciones inventory_*() de act_cx_resources_deploy.py (READ-ONLY, una función por tipo de recurso). Si algún LIST falla → abortar inmediatamente, sin datos parciales.
Por qué existe

Si desplegamos sin saber el estado actual, no podemos comparar qué ha cambiado. Esta foto es el punto de partida de todo el pipeline — sin ella, el diff no tiene contra qué comparar.

Qué necesita

Credenciales válidas para conectar con CX. Si no hay conexión o las credenciales han expirado, el paso falla aquí y no continúa.

Token de gcloud auth print-access-token. Configuración del agente (ID, región, proyecto) desde definitions/agent.yaml.
Qué produce

Una lista completa de los 12 tipos de recursos del agente (Playbooks, Examples, Tools, Flows, Pages, Intents, Entity Types, Webhooks, Generators, Agent Config, Environments, Versions), con el conteo de cada uno. Esta lista es el punto de referencia que el Paso 3 usa para calcular qué ha cambiado.

Persiste en docs/data/act_cx_draft_resources_inventory.json (generado, en .gitignore). Estructura: { generated_at, agent, totals: { playbooks: N, ... }, resources: { playbooks: [...], ... } }
Flujo del paso

1. Inicial — botón "Iniciar inventario →"
2. Corriendo — log animado con las llamadas LIST a la API (12 tipos de recursos)
3. Completado — banner ✓ + cuadrícula de 12 stat-cards con conteos + botón "Continuar →"
4. Error — si algún LIST falla → paso en error, no continúa al Paso 2

Criterios de validación

✓ LIST completado para los 12 tipos de recursos
✓ Token de auth válido — sin errores 401/403
✓ Si cualquier LIST falla → abortar inmediatamente, no continuar con datos parciales
✓ Al menos un tipo devuelve recursos — el agente no está vacío
✓ Si draft difiere de staging (deploy anterior incompleto) → el inventario refleja el draft, no staging
✓ 429 (rate limit) → reintentar con backoff exponencial (máx. 3 intentos); si persiste → abortar

Integridad del JSON generado

Antes de guardar el archivo, el sistema verifica que los datos son coherentes y completos — así el Paso 3 puede confiar en ellos sin comprobaciones adicionales.

✓ Los 12 tipos presentes en resources como arrays (null ≠ [] — null = fallo, [] = tipo inexistente)
✓ totals[tipo] == len(resources[tipo]) para cada tipo — detecta paginación incompleta
✓ Todos los ítems con count > 0 tienen name no vacío — el diff usa name como clave
✓ generated_at, agent y totals presentes y válidos; agent no es un placeholder

Qué hace

Tienes cambios en tu rama staging local que todavía no están en GitHub. Este paso los sube a GitHub staging para que el pipeline pueda comparar contra CX.

El script ejecuta git push origin staging, empujando los commits de staging local a origin/staging en GitHub. El usuario ve el log del resultado.
Por qué existe

El diff del Paso 3 compara GitHub staging contra el draft de CX. Si los commits no están en GitHub todavía, el diff estaría comparando contra código desactualizado.

Qué necesita

Acceso a GitHub con commits pendientes de push. Sin conflictos con el remoto.

Sin conflictos con origin/staging. Si el remoto está adelantado → abortar; resolver con pull antes de continuar.
Qué produce

La rama staging de GitHub actualizada. A partir de aquí el Paso 3 ya tiene contra qué comparar.

Detalle técnico
git push origin staging — si ya está al día ("Everything up-to-date") el paso completa. Si hay conflicto con origin/staging → abortar; el usuario resuelve antes de continuar.
Flujo del paso

1. Inicial — status ✗ con commits pendientes, lista de commits, botón "Hacer push →"
2. Ya al día — si 0 commits pendientes: status ✓, botón "Continuar →" directamente
3. Corriendo — log animado del push en curso
4. Éxito — status ✓, botón "Continuar →"
5. Error — mensaje de fallo (conflicto o red), botón "Reintentar"

Criterios de validación

✓ Push exitoso — sin errores de red ni de permisos
✓ origin/staging al día con staging local
✓ Si hay conflicto → abortar, no continuar
✓ Path de error validado con PUSH_SIMULATE_FAIL=true — el sistema detecta el fallo, muestra el error y no continúa al Paso 3
✓ Si ya está al día (0 commits pendientes) → el paso completa sin error — no bloquea el pipeline

Paso 3 — Diff GitHub vs CX
Qué hace

Antes de tocar nada en CX, el sistema compara lo que tienes en GitHub staging con lo que hay ahora mismo en el draft del agente. El resultado es una lista exacta: qué recursos hay que crear, cuáles modificar y cuáles eliminar. Solo se opera sobre lo que ha cambiado.

Diff entre definitions/ de GitHub staging y el inventario del Paso 1 (act_cx_draft_resources_inventory.json). Genera POST (nuevo), PATCH (modificado), DELETE (eliminado). Matching por campo name.
Por qué existe

Si desplegaras todo siempre estarías machacando recursos que no han cambiado, arriesgando inconsistencias. El diff es lo que hace que el pipeline sea idempotente: ejecutarlo dos veces seguidas sin cambios no hace nada.

Qué necesita

El inventario generado en el Paso 1 como foto del estado actual del draft, y los archivos de definición de GitHub staging como fuente de verdad de lo que debería haber.

act_cx_draft_resources_inventory.json · definitions/**/*.yaml (rama staging)
Qué produce

Una lista de operaciones por recurso: POST · PATCH · DELETE. Si no hay diferencias, el pipeline termina aquí — no hay nada que desplegar.

Flujo del paso

1. Con cambios — tabla con Tipo · Recurso · Operación + leyenda POST/PATCH/DELETE + botón "Continuar →"
2. Sin cambios — aviso "Sin cambios detectados" + botón "Cerrar" → pipeline termina

Criterios de validación

✓ Diff completado para los 12 tipos de recursos
✓ POST/PATCH/DELETE mutuamente excluyentes por recurso
✓ Tabla coherente con el inventario del Paso 1
✓ Si sin cambios → pipeline termina limpiamente, no continúa al Paso 4

Paso 4 — Confirmar deploy
Qué hace

Aplica al draft del agente en CX los cambios calculados en el Paso 3, recurso a recurso. Es el único paso que realmente muta CX — todo lo anterior era preparación.

Para cada recurso en la lista del Paso 3: POST (nuevo), PATCH (modificado) o DELETE (eliminado). Playbooks y pages usan Full Update: GET del objeto completo → modificar → PATCH sin updateMask. Bug conocido del backend CX en europe-west1: PATCH con updateMask falla silenciosamente. Si un recurso falla, los siguientes quedan "no intentados". Orden de deploy obligatorio: Entity Types → Intents → Webhooks → Tools → Generators → Playbooks → Examples → Flows → Pages → Agent Config. Los tipos que son referenciados por otros van primero — si un playbook referencia un webhook, el webhook debe existir antes del PATCH del playbook.
Por qué existe

Sin este paso el diff no sirve de nada. Es el momento en que los cambios pasan de GitHub al agente.

Qué necesita

La lista de operaciones del Paso 3 y conexión activa con CX.

Lista POST/PATCH/DELETE del Paso 3. Token de gcloud auth print-access-token. Headers obligatorios (ver Specs generales).
Qué produce

El draft del agente en CX actualizado con los cambios. Si falla en algún recurso, el draft queda en estado parcial — algunos recursos aplicados, otros no — con dos salidas de recuperación.

Flujo del paso

El recuento y descripción de recursos (X modificados, Y nuevos, Z eliminados) viene del diff del Paso 3 — el script lo pasa a la UI antes de mostrar el gate de confirmación. El log de ejecución se emite línea a línea, una por recurso, de forma progresiva — no como resumen final. El resto de estados y botones son derivables del HTML.

Criterios de validación

✓ Deploy completo → todos los recursos OK, banner verde, botón "Continuar →"
✓ Deploy parcial → resumen OK/ERROR/no-intentado, dos opciones de recuperación
✓ "Reintentar fallidos" → reintenta el recurso fallido más todos los que quedaron como "no intentado" por el fallo anterior; no reintenta los que ya completaron OK
✓ "Revertir draft" → restaura el draft al estado previo al deploy
✓ Simulable con DEPLOY_SIMULATE_FAIL=true

Paso 5 — Snapshot del agente
Qué hace

CX congela el estado actual del draft como una versión numerada en el entorno staging. A partir de aquí los tests tienen una referencia estable — el draft ya no importa porque el snapshot es inmutable.

POST /versions en el entorno staging → devuelve una LRO. Polling en GET /operations/{id} hasta done:true. displayName obligatorio en el body — sin él la API devuelve 200 pero la operation falla silenciosamente con code:3.
Por qué existe

El draft es mutable y puede cambiar en cualquier momento. El snapshot congela el estado para que los tests tengan una referencia fija y es el punto de rollback si los tests fallan en el Paso 6.

Qué necesita

Conexión activa con CX. El nombre del snapshot es opcional — si el usuario lo deja vacío, el script genera uno automático.

Nombre → campo displayName en el POST body. Máx. 64 chars, letras/dígitos/guiones/guiones bajos. Si vacío → el script genera un nombre automático con fecha y hora; el campo nunca se omite del body.
Qué produce

Una nueva versión del agente en staging. La versión anterior se conserva para poder hacer rollback. El nombre del snapshot queda disponible para los Pasos 6, 7 y 8.

CX conserva máximo 5 versiones por entorno. Si ya hay 5, la más antigua se elimina automáticamente al crear ésta. El script almacena el nombre del snapshot en memoria para propagarlo a los pasos siguientes.
Flujo del paso

El nombre que el usuario introduce (o vacío) se envía como displayName en el POST. Si está vacío, el script genera el nombre automáticamente — el campo nunca se omite. El resultado del LRO confirma el nombre final asignado por CX.

Criterios de validación

✓ Snapshot creado → esperar done:true en el LRO antes de reportar éxito — no reportar antes
✓ displayName siempre presente en el POST body — nunca omitirlo aunque el campo UI esté vacío
✓ Si ya hay 5 versiones → la más antigua se elimina automáticamente, el snapshot se crea igualmente
✓ El nombre del snapshot se propaga a los elementos snapshot-name-ref de Pasos 6, 7 y 8

Paso 6 — Validación de tests
Qué hace

Este paso no ejecuta tests — es el punto de decisión donde el usuario declara si los tests QA han pasado o fallado en staging. Según la respuesta, el pipeline avanza o revierte.

Por qué existe

El pipeline no puede ejecutar los tests QA por sí solo — requieren un runner externo. Este gate obliga a verificar los resultados antes de permitir el avance a producción.

Qué necesita

El snapshot creado en el Paso 5, necesario para poder hacer rollback si los tests fallan. El usuario habrá ejecutado la suite QA externamente antes de llegar aquí.

Qué produce

Dos salidas posibles: si los tests pasan, el pipeline avanza al Paso 7. Si se confirma rollback, staging vuelve a la versión anterior, el draft queda restaurado y el pipeline se aborta.

Rollback: PATCH /environments/staging apuntando a la versión anterior + restaurar draft desde esa versión. Si el usuario cancela el rollback: ninguna llamada a la API — staging y draft quedan sin cambios.
Flujo del paso

La decisión del usuario (superados / fallidos) determina el camino. Si rollback confirmado: el script hace PATCH sobre staging y restaura el draft — el pipeline queda abortado. Si rollback cancelado: el pipeline queda en pausa con el snapshot actual intacto.

Criterios de validación

✓ "Tests superados" → avanza al Paso 7 sin ninguna llamada a la API
✓ Rollback confirmado → staging apunta a la versión anterior + draft restaurado desde esa versión
✓ Rollback cancelado → staging y draft no se modifican
✓ Producción no se toca en ningún caso durante este paso

Paso 7 — Gate QA staging
Qué hace

El usuario valida directamente el agente en el entorno staging de CX. La UI muestra el estado actual de los tres entornos (draft, staging, producción) para dar contexto completo. Cuando el usuario confirma, el pipeline avanza a producción. Si algo falla en las pruebas, puede revertir staging a la versión anterior desde este mismo paso.

Por qué existe

Antes de impactar a usuarios reales, este paso ofrece una última barrera de validación humana con el snapshot real activo en staging — no en simulación. El Paso 6 valida con tests automatizados; este paso valida con exploración manual directa en CX.

Qué necesita

El snapshot del Paso 5 activo en el entorno staging. El usuario habrá probado el agente en CX antes de pulsar "Validado".

Qué produce

Dos salidas posibles: si el usuario valida, el pipeline avanza al Paso 8 sin ninguna llamada a la API. Si el usuario revierte, staging vuelve a la versión anterior, el draft queda restaurado y el pipeline se aborta — misma secuencia que el rollback del Paso 6.

"Validado" → advance(7) sin ninguna llamada a API. "Rollback a staging anterior" → PATCH /environments/staging apuntando a la versión anterior + restaurar draft desde esa versión. Misma secuencia que rollbackStaging() del Paso 6.
Flujo del paso

El bloque de estado de entornos muestra las tres filas (draft, staging, producción) con la versión activa en cada una, para que el usuario tenga el contexto completo antes de decidir. El enlace abre directamente el agente en CX staging. No hay lógica automática en este paso.

Criterios de validación

✓ "Validado" → avanza al Paso 8 sin llamadas a la API
✓ Rollback → PATCH /environments/staging a versión anterior + draft restaurado desde esa versión
✓ Producción no se modifica en ningún caso durante este paso
✓ Tras rollback, el pipeline queda abortado — no pausado

Paso 8 — Aprobar subida a producción
Qué hace

Ejecuta las dos acciones que llevan los cambios a producción: merge de la rama staging a main en GitHub, y promoción del snapshot activo al entorno de producción en CX. Se ejecutan en secuencia: si el merge falla, la promoción no se intenta.

Por qué existe

Separa la aprobación definitiva del resto del pipeline. En este punto el usuario tiene toda la información necesaria — staging validado manualmente, snapshot conocido — antes de tomar la decisión que impacta a usuarios reales.

Qué necesita

El snapshot del Paso 5 activo en staging. La rama staging sin conflictos con main en GitHub — si los hay, el merge falla y el paso lo indica.

Qué produce

Si ambas acciones tienen éxito: el snapshot queda asignado a producción, staging mergeado a main, pipeline completado. Si el merge falla por conflicto: el pipeline se detiene y el usuario resuelve en GitHub antes de reintentar — la promoción a CX no se ejecuta hasta que el merge complete.

Acción 1: merge staging → main vía GitHub API (o gh pr merge). Si el merge devuelve conflicto, mostrar panel y detener. Acción 2: PATCH /environments/production apuntando al mismo snapshot que ya tiene staging — no se crea una versión nueva, solo se reasigna el entorno. Si la rama staging diverge o hay conflictos, el merge falla antes de tocar CX producción. Si el merge falla → main no ha sido modificado. El abort es limpio — no requiere acción de recuperación en GitHub.
Flujo del paso

Las dos acciones se emiten progresivamente en el log, una tras otra. Si el merge falla por conflicto, el panel de conflicto reemplaza el log y muestra el enlace a GitHub para resolverlo — el usuario puede reintentar desde el mismo estado. "Abortar" en ese panel solo cancela el intento de merge; staging y su snapshot quedan intactos y el gate inicial reaparece.

Criterios de validación

✓ Merge primero, promoción después — nunca en paralelo ni al revés
✓ Si merge falla → PATCH /environments/production no se ejecuta
✓ "Abortar" en conflicto no inicia rollback — solo restaura el gate inicial
✓ El snapshot asignado a producción es el mismo que ya tiene staging (sin crear versión nueva)
✓ Producción solo se modifica si el merge completó sin errores
