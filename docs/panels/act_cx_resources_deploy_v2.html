Specs por paso
Paso 1 — Inventario CX
Qué hace

Construye el punto de partida del pipeline, y hace tres cosas: averigua qué repositorio corresponde al agente elegido, fotografía el draft de CX y lee el repositorio entero para emparejar cada resource con su archivo. Lo que sale no es una lista de lo que hay en CX, sino el mapa de qué está en los dos sitios, qué solo en CX y qué solo en el repositorio.

Por qué existe

Sin saber el estado actual no hay nada contra qué comparar. Pero una foto de CX a secas tampoco basta: hasta que cada resource no está emparejado con su archivo, no se puede distinguir un cambio de un resource nuevo, ni un renombrado de un borrado más una creación. El emparejamiento se hace aquí para que el paso siguiente solo tenga que comparar contenidos.

Qué produce

El mapa del agente en tres grupos —emparejados, solo en CX, solo en el repositorio— con el archivo de cada uno. Lleva dentro el proyecto, el agente, el repositorio, el commit de staging del que se leyó y la marca de tiempo.

El Paso 2 no vuelve a leer nada: trabaja sobre este mismo mapa. Releer arriesgaría comparar contra una foto distinta de la que el usuario aprobó.
Qué escribe y dónde

Nada. Consulta el mapeo agente-repositorio, lee CX y lee GitHub, pero no modifica ninguno de los tres. Es lo que declara la etiqueta solo lectura de la cabecera.

1.1 — Resolución del repositorio

Al elegir el agente aparece su repositorio. No hay selector: el mapeo lo guarda el servidor, y un agente tiene como máximo un repositorio — eso es lo que impide que dos repositorios reclamen el mismo agente.

Si el agente no tiene ninguno, se muestra el aviso y el botón de iniciar queda deshabilitado. Si ningún agente del proyecto lo tiene, el aviso aparece arriba al elegir proyecto, para no tener que recorrerlos uno a uno para descubrirlo.

El mapeo vive fuera del ciclo de vida del servidor, así que sobrevive a que el contenedor se recicle.
Cuando no hay entrada, devolver un error tipado que el panel distinga de un fallo de red — solo así puede ofrecer el enlace a vincular en lugar de un mensaje genérico.
1.2 — Comprobación de conexión

Primera línea del log. Verifica credenciales y acceso al agente antes de lanzar ninguna lectura. Si falla aquí, el error es inmediato y distingue las dos causas —sin credenciales, o sin permiso sobre ese proyecto— en vez de aparecer a mitad del inventario como un 401 sin contexto.

1.3 — Foto de CX

Una lectura por cada tipo de resource declarado, sobre el draft — el estado editable, no lo que corre en staging. Los tipos salen del registro, así que el número no es fijo.

Si una lectura falla, se aborta. Mejor sin datos que con datos parciales: un inventario incompleto produce un diff que propone crear lo que ya existe.

1.4 — Lectura del repositorio

Se leen todos los YAML del repositorio, de forma recursiva. La estructura de carpetas es libre y no significa nada: cada archivo declara en su metadata qué tipo de resource es, de quién cuelga y a qué resource de CX corresponde.

Dos situaciones paran el paso con error explícito, nunca en silencio: un archivo sin tipo —sería invisible para el pipeline— y dos archivos con el mismo identificador de CX, que es lo que ocurre al duplicar un archivo y olvidar vaciarlo.

La lectura tiene que ser recursiva de verdad: un listado que solo devuelva el primer nivel de cada carpeta deja fuera todo lo anidado, y eso incluye los examples, que cuelgan de su playbook.
La rama es staging, y el commit del que se leyó viaja en el resultado.
1.5 — Emparejamiento

Cada resource de CX se empareja con su archivo por identificador, no por nombre ni por ubicación. El resultado son los tres grupos, cada uno desplegable para ver la lista completa.

Emparejado — está en CX y tiene archivo.
Solo en CX — existe en el agente y ningún archivo lo reclama.
Solo en el repositorio — tiene archivo pero aún no existe en CX, o su identificador ya no está allí.

Por identificador y no por nombre: yendo por nombre, renombrar algo en CX parecería un recurso borrado más uno creado, y el pipeline propondría destruir y recrear en vez de cambiar un campo.
Criterios de validación

✓ Agente sin repositorio → el paso no arranca y ofrece vincular, en vez de fallar con un error de red
✓ Ningún agente del proyecto con repositorio → aviso al elegir proyecto
✓ Un archivo sin tipo → parada con error que nombre el archivo
✓ Dos archivos con el mismo identificador → parada con error que nombre los dos
✓ Los tres grupos suman el total de resources leídos
✓ Repositorio sin rama staging → mensaje que lo diga con esas palabras, no un 404 genérico
✓ Fallo de GitHub a mitad de la lectura → abortar sin mapa, nunca con el repositorio a medio leer
✓ Fallo de una lectura de CX → abortar de inmediato, sin datos parciales
✓ Agente vacío → aviso en el log, nunca aborta: un agente recién creado puede estarlo legítimamente
✓ Límite de peticiones alcanzado → reintentar con espera creciente; si persiste, abortar

Paso 2 — Diff GitHub vs CX
Qué hace

Antes de tocar nada en CX, el sistema compara lo que tienes en GitHub staging con lo que hay ahora mismo en el draft del agente. El resultado es una lista exacta: qué recursos hay que crear, cuáles modificar y cuáles eliminar. Solo se opera sobre lo que ha cambiado.

Diff entre definitions/ de GitHub staging y el inventario del Paso 1 (act_cx_draft_resources_inventory_<project>_<agent>.json). Genera POST (nuevo), PATCH (modificado), DELETE (eliminado). Matching por campo displayName — name lo asigna CX al crear el recurso (incluye un identificador que ningún YAML local puede conocer de antemano), así que no sirve como clave de comparación.
Por qué existe

Si desplegaras todo siempre estarías machacando recursos que no han cambiado, arriesgando inconsistencias. El diff es lo que hace que el pipeline sea idempotente: ejecutarlo dos veces seguidas sin cambios no hace nada.

Qué necesita

El inventario generado en el Paso 1 como foto del estado actual del draft, y los archivos de definición de GitHub staging como fuente de verdad de lo que debería haber.

act_cx_draft_resources_inventory_<project>_<agent>.json · definitions/**/*.yaml (rama staging)
Qué produce

Una lista de operaciones por recurso: POST · PATCH · DELETE. Si no hay diferencias, el pipeline termina aquí — no hay nada que desplegar.

Flujo del paso

1. Con cambios — tabla con Tipo · Recurso · Operación + leyenda POST/PATCH/DELETE + botón "Continuar →"
2. Sin cambios — aviso "Sin cambios detectados" + botón "Cerrar" → pipeline termina

Criterios de validación

✓ Diff completado para los 12 tipos de recursos
✓ POST/PATCH/DELETE mutuamente excluyentes por recurso
✓ Tabla coherente con el inventario del Paso 1
✓ Si sin cambios → pipeline termina limpiamente, no continúa al Paso 3

Paso 3 — Confirmar deploy
Qué hace

Aplica al draft del agente en CX los cambios calculados en el Paso 2, recurso a recurso. Es el único paso que realmente muta CX — todo lo anterior era preparación.

Recuperación tras un fallo parcial: no existe «revertir draft» ni se necesita. Dos caminos, medidos contra la API: Reintentar fallidos reutiliza la lista del Paso 2 y solo toca los ERROR y los no intentados; empezar de nuevo desde el Paso 1 refresca la foto de CX y el diff propone solo lo que de verdad falta. Lo que no vale es relanzar solo el Paso 2: ese paso no consulta CX, lee el JSON que escribió el Paso 1, y con la foto caducada un POST ya aplicado se reintenta y choca con un 409. Para deshacer algo aplicado correctamente, se corrige el YAML y se despliega otra vez.

Para cada recurso en la lista del Paso 2: POST (nuevo), PATCH (modificado) o DELETE (eliminado). Playbooks y pages usan Full Update: GET del objeto completo → modificar → PATCH sin updateMask. Bug conocido del backend CX en europe-west1: PATCH con updateMask falla silenciosamente. Si un recurso falla, los siguientes quedan "no intentados". Orden de deploy obligatorio: Entity Types → Intents → Webhooks → Tools → Generators → Playbooks → Examples → Flows → Pages → Agent Config. Los tipos que son referenciados por otros van primero — si un playbook referencia un webhook, el webhook debe existir antes del PATCH del playbook.
Por qué existe

Sin este paso el diff no sirve de nada. Es el momento en que los cambios pasan de GitHub al agente.

4.0 — Comprobación CX → repo (antes del gate)

Antes de dejar confirmar, el sistema mira en la dirección contraria al diff: qué existe o difiere en CX que definitions/ no recoge. El deploy sincroniza repo → CX, así que todo lo que esté solo en CX se borra al aplicar. Sin este aviso, el trabajo hecho desde la consola desaparece en silencio.

Si hay diferencias, el gate de confirmación no se muestra hasta que el usuario elija: traerlas al repo primero, o continuar aceptando que se pierden. Si no hay ninguna, se indica y el gate aparece con normalidad.

Recorre el inventario del Paso 1 y, por cada tipo, marca: recursos presentes en CX y ausentes de definitions/ (los que el diff propone como DELETE), y campos con contenido en CX que el YAML no declara — estos últimos el diff no los ve, porque solo compara los campos que el local menciona.
No usa el diff del Paso 2 como fuente: ese mira repo → CX y por diseño es ciego a lo que el repo no nombra.
«Traer al repo» tiene un alcance acotado: solo actualiza campos de recursos que ya existen en definitions/ (por ejemplo añadir referencias que faltan a un playbook). Un recurso que solo vive en CX exigiría crear un archivo nuevo y queda fuera — esos ya salen como DELETE en el diff, y traerlos contradiría esa decisión. El botón se deshabilita si no hay nada actualizable.
Nunca escribe directo: genera los cambios, los muestra campo a campo (valor actual y líneas a añadir) y espera confirmación, como cualquier modificación de definitions/ (CLAUDE.md §7.4). Al guardar, el diff se recalcula contra el repo ya actualizado.
Qué necesita

La lista de operaciones del Paso 2 y conexión activa con CX.

Lista POST/PATCH/DELETE del Paso 2. Token de gcloud auth print-access-token. Headers obligatorios (ver Specs generales).
Qué produce

El draft del agente en CX actualizado con los cambios. Si falla en algún recurso, el draft queda en estado parcial — algunos recursos aplicados, otros no — con dos salidas de recuperación.

Flujo del paso

El recuento y descripción de recursos (X modificados, Y nuevos, Z eliminados) viene del diff del Paso 2 — el script lo pasa a la UI antes de mostrar el gate de confirmación. El log de ejecución se emite línea a línea, una por recurso, de forma progresiva — no como resumen final. El resto de estados y botones son derivables del HTML.

Criterios de validación

✓ Comprobación CX → repo ejecutada antes del gate; si hay diferencias, el gate no aparece hasta elegir
✓ Diferencias listadas con tipo, recurso, qué cambia y si se puede traer al repo
✓ "Traer al repo" muestra los cambios antes de escribir nada, con opción de cancelar
✓ Deploy completo → todos los recursos OK, banner verde, botón "Continuar →"
✓ Deploy parcial → resumen OK/ERROR/no-intentado, dos opciones de recuperación
✓ "Reintentar fallidos" → reintenta el recurso fallido más todos los que quedaron como "no intentado" por el fallo anterior; no reintenta los que ya completaron OK
✓ No hay opción de revertir el draft, y no hace falta: el draft no lo ve ningún usuario y el pipeline es idempotente
✓ Simulable con DEPLOY_SIMULATE_FAIL=true

Paso 4 — Snapshot del agente
Qué hace

CX congela el estado actual del draft como una versión numerada en el entorno staging. A partir de aquí los tests tienen una referencia estable — el draft ya no importa porque el snapshot es inmutable.

Dos llamadas, en orden — ninguna sustituye a la otra: 1) POST /versions sobre cada flow que tenga cambios — versions cuelga del flow, no del agente. Hoy Petal solo tiene default_start_flow, pero no lo fijes como constante: recorre los flows que existan de verdad. Cada llamada devuelve una LRO. Polling en GET /operations/{id} hasta done:true. displayName obligatorio en el body — sin él la API devuelve 200 pero la operation falla silenciosamente con code:3. 2) PATCH /environments/staging apuntando a la versión recién creada — sin este segundo paso, la versión existe pero staging sigue enseñando la anterior, y los Pasos 6-7 (que validan "lo que hay en staging") estarían probando la versión vieja, no la nueva.
Por qué existe

El draft es mutable y puede cambiar en cualquier momento. El snapshot congela el estado para que los tests tengan una referencia fija y es el punto de rollback si los tests fallan en el Paso 5.

Qué necesita

Conexión activa con CX. El nombre del snapshot es opcional — si el usuario lo deja vacío, el script genera uno automático.

Nombre → campo displayName en el POST body. Máx. 64 chars, letras/dígitos/guiones/guiones bajos. Si vacío → el script genera un nombre automático con fecha y hora; el campo nunca se omite del body.
Qué produce

Una nueva versión del agente en staging. La versión anterior se conserva para poder hacer rollback. El nombre del snapshot queda disponible para los Pasos 6, 7 y 8.

Medido contra la API: un flow admite 20 versiones y el límite es duro — la 21 falla con code:9. CX no rota nada por su cuenta; la documentación que decía 5 y decía que se borraban solas era falsa en las dos mitades.
El pipeline mantiene un pool de 5 versiones propias, reconocibles por el prefijo deploy_, y borra la más antigua antes de crear la sexta. No toca ninguna otra: renombrar una versión la saca del pool para siempre, y las que un entorno esté sirviendo quedan protegidas aunque lleven el prefijo. La protección es opt-out y no opt-in a propósito — olvidarse de marcar algo no puede costar una versión.
El script almacena el nombre del snapshot en memoria para propagarlo a los pasos siguientes.
Flujo del paso

El nombre que el usuario introduce (o vacío) se envía como displayName en el POST. Si está vacío, el script genera el nombre automáticamente — el campo nunca se omite. El resultado del LRO confirma el nombre final asignado por CX.

Criterios de validación

✓ Pool automático de 5: al crear la sexta, se borra la más antigua de las creadas por el pipeline
✓ Una versión guardada (renombrada) nunca rota, y una fijada por un entorno tampoco aunque lleve el prefijo
✓ Snapshot creado → esperar done:true en el LRO antes de reportar éxito — no reportar antes
✓ displayName siempre presente en el POST body — nunca omitirlo aunque el campo UI esté vacío
✓ Si ya hay 5 versiones → la más antigua se elimina automáticamente, el snapshot se crea igualmente
✓ El nombre del snapshot se propaga a los elementos snapshot-name-ref de Pasos 6, 7 y 8

Paso 5 — Validación de tests
Qué hace

Este paso no ejecuta tests — es el punto de decisión donde el usuario declara si los tests QA han pasado o fallado en staging. Según la respuesta, el pipeline avanza o revierte.

Por qué existe

El pipeline no puede ejecutar los tests QA por sí solo — requieren un runner externo. Este gate obliga a verificar los resultados antes de permitir el avance a producción.

Qué necesita

El snapshot creado en el Paso 4, necesario para poder hacer rollback si los tests fallan. El usuario habrá ejecutado la suite QA externamente antes de llegar aquí.

Qué produce

Dos salidas posibles: si los tests pasan, el pipeline avanza al Paso 6. Si se confirma rollback, staging vuelve a la versión anterior, el draft queda restaurado y el pipeline se aborta.

Rollback: PATCH /environments/staging apuntando a la versión anterior + restaurar draft desde esa versión. Si el usuario cancela el rollback: ninguna llamada a la API — staging y draft quedan sin cambios.
Flujo del paso

La decisión del usuario (superados / fallidos) determina el camino. Si rollback confirmado: el script hace PATCH sobre staging y restaura el draft — el pipeline queda abortado. Si rollback cancelado: el pipeline queda en pausa con el snapshot actual intacto.

Criterios de validación

✓ "Tests superados" → avanza al Paso 6 sin ninguna llamada a la API
✓ Rollback confirmado → staging apunta a la versión anterior + draft restaurado desde esa versión
✓ Rollback cancelado → staging y draft no se modifican
✓ Producción no se toca en ningún caso durante este paso

Paso 6 — Gate QA staging
Qué hace

El usuario valida directamente el agente en el entorno staging de CX. La UI muestra el estado actual de los tres entornos (draft, staging, producción) para dar contexto completo. Cuando el usuario confirma, el pipeline avanza a producción. Si algo falla en las pruebas, puede revertir staging a la versión anterior desde este mismo paso.

Por qué existe

Antes de impactar a usuarios reales, este paso ofrece una última barrera de validación humana con el snapshot real activo en staging — no en simulación. El Paso 5 valida con tests automatizados; este paso valida con exploración manual directa en CX.

Qué necesita

El snapshot del Paso 4 activo en el entorno staging. El usuario habrá probado el agente en CX antes de pulsar "Validado".

Qué produce

Dos salidas posibles: si el usuario valida, el pipeline avanza al Paso 7 sin ninguna llamada a la API. Si el usuario revierte, staging vuelve a la versión anterior, el draft queda restaurado y el pipeline se aborta — misma secuencia que el rollback del Paso 5.

"Validado" → advance(7) sin ninguna llamada a API. "Rollback a staging anterior" → PATCH /environments/staging apuntando a la versión anterior + restaurar draft desde esa versión. Misma secuencia que rollbackStaging() del Paso 5.
Flujo del paso

El bloque de estado de entornos muestra las tres filas (draft, staging, producción) con la versión activa en cada una, para que el usuario tenga el contexto completo antes de decidir. El enlace abre directamente el agente en CX staging. No hay lógica automática en este paso.

Criterios de validación

✓ "Validado" → avanza al Paso 7 sin llamadas a la API
✓ Rollback → PATCH /environments/staging a versión anterior + draft restaurado desde esa versión
✓ Producción no se modifica en ningún caso durante este paso
✓ Tras rollback, el pipeline queda abortado — no pausado

Paso 7 — Aprobar subida a producción
Qué hace

Ejecuta las dos acciones que llevan los cambios a producción: merge de la rama staging a main en GitHub, y promoción del snapshot activo al entorno de producción en CX. Se ejecutan en secuencia: si el merge falla, la promoción no se intenta.

Por qué existe

Separa la aprobación definitiva del resto del pipeline. En este punto el usuario tiene toda la información necesaria — staging validado manualmente, snapshot conocido — antes de tomar la decisión que impacta a usuarios reales.

Qué necesita

El snapshot del Paso 4 activo en staging. La rama staging sin conflictos con main en GitHub — si los hay, el merge falla y el paso lo indica.

Qué produce

Si ambas acciones tienen éxito: el snapshot queda asignado a producción, staging mergeado a main, pipeline completado. Si el merge falla por conflicto: el pipeline se detiene y el usuario resuelve en GitHub antes de reintentar — la promoción a CX no se ejecuta hasta que el merge complete.

Acción 1: merge staging → main vía GitHub API (o gh pr merge). Si el merge devuelve conflicto, mostrar panel y detener. Acción 2: PATCH /environments/production apuntando al mismo snapshot que ya tiene staging — no se crea una versión nueva, solo se reasigna el entorno. Si la rama staging diverge o hay conflictos, el merge falla antes de tocar CX producción. Si el merge falla → main no ha sido modificado. El abort es limpio — no requiere acción de recuperación en GitHub.
Flujo del paso

Las dos acciones se emiten progresivamente en el log, una tras otra. Si el merge falla por conflicto, el panel de conflicto reemplaza el log y muestra el enlace a GitHub para resolverlo — el usuario puede reintentar desde el mismo estado. "Abortar" en ese panel solo cancela el intento de merge; staging y su snapshot quedan intactos y el gate inicial reaparece.

Criterios de validación

✓ Merge primero, promoción después — nunca en paralelo ni al revés
✓ Si merge falla → PATCH /environments/production no se ejecuta
✓ "Abortar" en conflicto no inicia rollback — solo restaura el gate inicial
✓ El snapshot asignado a producción es el mismo que ya tiene staging (sin crear versión nueva)
✓ Producción solo se modifica si el merge completó sin errores

Pipeline completado
Estado final

Staging y producción apuntan al mismo snapshot. El código validado está en main. El deploy queda registrado con timestamp.

Estado final de entornos: staging → <snapshot> · production → <snapshot>. La rama main tiene el commit de merge. El checkbox "Sincronizar main local" recuerda al operador hacer git fetch origin main:main en su copia local — es manual, no lo hace el script.
